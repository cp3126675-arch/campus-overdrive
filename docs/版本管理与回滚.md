## 每次更新

1. 保留线上原包、源码和部署提交，创建功能分支，不覆盖历史版本。
2. 更新 `public/version.json` 和 CHANGELOG.md。游戏主菜单显示版本号。
3. 执行 `npm test`、`npm run check`、`node scripts/export-static.mjs --github-pages`、`npm run build`。保存测试日志；列明未做的检查。
4. 提交源码后，使用 `python3 scripts/release.py snapshot VERSION --archive ZIP_PATH --source-ref COMMIT --evidence LOG_PATH` 封存到 `outputs/releases/VERSION/`。目录含源码 tar.gz、原始 ZIP、逐文件校验清单和测试证据。已存在版本拒绝覆盖。
5. 每次上传时更新 GitHub 根目录 RELEASES.md，提交标题带版本号。部署核验后创建对应 GitHub Release 与标签（v版本号），写明变更和上一版恢复信息，不覆盖已发布标签。
6. 上传封存 ZIP，确认部署成功，并逐文件核对线上 SHA256；记录发布回执到 `docs/releases/`。候选包的构建与测试完成不代表已上线。

## 不满意时如何回滚

告诉协作者“回滚到 0.2.0”即可执行以下流程，保留 0.3.0 供以后恢复。

### GitHub Actions 恢复历史包

在仓库 Actions → Publish campus game → Run workflow，`restore_commit` 填写目标历史部署提交的完整 40 位 SHA。例如旧版：

`696077825cb6648871c95803af1afd21c2465f83`

填写旧版的 `expected_sha256`（见上文），然后运行。工作流读取该提交里的原始 `campus-game.zip` 并重新部署，不改源码历史、不强制推送。完成后核对游戏版本/资源哈希。留空 restore_commit 则发布当前 main 的 ZIP，可恢复新版。

这是重新部署历史包，不会改变 main 指向的 ZIP。未来 main 上有新的 ZIP 提交仍会自动发布；每次发布必须先查看最近部署回执。

### 本地兜底（工作流不可用时）

执行 `python3 scripts/release.py prepare-rollback 0.2.0`。该命令先验证归档，再生成一个独立回滚目录，含 `campus-game.zip`、解压预览和回滚清单。它不会改当前代码或线上站点。

把生成的 ZIP 上传替换 GitHub 主分支同名文件，提交说明写“Rollback to 0.2.0”；等待部署完成并核验。这是新提交，历史仍可追溯。

不要删除新版目录，不使用 `git reset --hard`，不依赖重新安装旧依赖来重建原包。归档记录在本机，GitHub 历史保留公开部署包；源码另可从本地标签或归档恢复。
